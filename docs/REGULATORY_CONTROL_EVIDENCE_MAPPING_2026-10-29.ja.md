## 4. 二つの判定を混ぜない

- **証拠の検証**：`VALID / INVALID / INDETERMINATE` は実行した署名・ハッシュ・記録関係の検査に限定する。外部アンカーがない場合、証拠全体は未確定のまま。
- **管理策の評価**：`PASS / FAIL / REVALIDATION_REQUIRED / UNASSESSABLE` は、本実証で定義した基準と、与えられた対象・版・設定・範囲に限定する。法令適合は常に `NOT_ASSESSED`。

正しく署名された「MFA無効」の観測は、証拠のローカル検証がVALIDでも管理策がFAILとなり得る。記録の署名が不正なら管理策は評価不能にする。未確認の項目があっても、別の項目の確認済みの不合格を消さない。

## 5. 変更後再評価の実証

`examples/control-revalidation/` に、AILEXの管理者・事件境界を想定した**合成シナリオ**を置く。本番AILEX、AWS/IAM、実事件資料、実際のMFA、EDRには接続しない。人が記述した観測値の状態遷移を試験するだけで、本番統制を検査するコレクターは未実装。

評価を対象サービス、環境、リリース、設定のハッシュ、範囲、基準版、変更世代、確認時刻・期限に結び付ける。設定変更後は再確認を要求する。設定を元に戻しても変更世代が異なるため、過去の合格を再利用しない。過去の署名記録は書き換えず、新たな観測・評価を追加する。

24時間の有効期限はシナリオ上の仮定で、PPCやVAPが定めた期限ではない。実運用ではリスク・収集間隔・変更検知能力・レビュー体制に応じて設定する。観測されない変更はこの仕組みでも検出できず、真の全イベント完全性も主張しない。

## 6. 本番接続前の受入条件

1. AILEX側の所有者が対象環境・試験アカウント・非破壊試験範囲を承認する。
2. コレクターの読み取り権限、観測境界、収集欠落の扱い、変更検知の遅延を定義する。
3. 認証情報・事件本文を証跡へ複製せず、必要な参照と最小限の操作情報だけを採用する。ハッシュ化だけで匿名化したと扱わない。
4. テスト鍵を廃し、鍵の保管、失効・更新、信頼設定の配布、外部アンカーを別途設計する。
5. 審査者の役割、例外承認、有効期間、評価停止条件を定める。関連当事者による実証を独立第三者認証と表示しない。
6. ソース/設定/根拠の版と実行結果を固定して、第三者が追試結果を提出できるようにする。

## 7. 原資料に対する限定的な修正メモ

旧RTS 25は過去の記録の参照として残し、現行の当て先を2025/1155へ分離する。EU AI Act Art.72/73の適用関係は、今回確認したChapter IIIの延期範囲からは推定せず、別途確認項目として残す。日本についてAI推進法の性質を安全管理措置一般へ拡張しない。

「提出記録が全部」という表現は、宣言された範囲とコミット済み集合に対する検査へ限定する。観測前の欠落や隠された変更まで否定できない。ScopeManifest/denial-symmetry等は、採択・研究・実装の状態を個別に確認するまで採択済み機能としない。原資料の他の法域・順位・統計・標準化状況は今回の全面検証対象外。

### 8.1 安全管理措置案の追加確認

[e-Govの案件240000133](https://public-comment.e-gov.go.jp/pcm/detail?CLASSNAME=PCMMSTDETAIL&Mode=0&id=240000133)で、通則編と特定個人情報ガイドライン（事業者編・行政機関等編）の3告示案への意見募集を確認した。受付は2026-10-29 00:00から2026-11-27 23:59まで。

新たに確認した[個人情報保護委員会の改訂概要](https://public-comment.e-gov.go.jp/pcm/download?seqNo=0000323105)は、ログ等の一定期間の保管を手法の例示に追加する（8頁）。また、近時の大量個人データの不正アクセス・漏えい等を踏まえ、当初2027年4月を予定していた施行を可能な限り前倒しする方針を示すが、新たな確定施行日はこの資料にない（2頁）。改訂は手法の例示の追加等であり、新たな規律を設けるものではないと明記されている（5頁）。

これは一般的な安全管理措置の具体化である。本追補ではAI固有の新義務、VAP採用義務、暗号学的な完全性証明や第三者認証の義務を確認したとは扱わない。以下のパナソニック事案がこの改訂の直接の原因であることも、確認資料からは判断しない。

同社は、AI事業者への照会により学習利用が無効だったこと、利用者による削除後も30日間保持されること、10月25日以降は事業者内でも保持されないことを説明している。一般公開や不正利用による具体的被害は公表時点で確認されていないとしている。これらは同社の調査・照会結果として扱う。本追補によって、外部事業者の全コピー・バックアップの消去を独立検証した、または具体的な法違反を認定したとはしない。

削除に関する証拠には、少なくとも「何を対象に要求したか」「誰がいつ受理・回答したか」「どの範囲をどの方法で確認したか」「何が未確認または保持例外か」を分けて残す。事業者が完了を回答しても、確認できないコピーまで消去済みへ格上げしない。自管理鍵の破棄を示すERASURE等の記録も、別の鍵・平文・外部バックアップを含む全コピー消去の証明に拡張しない。

証跡には個人情報の本文・認証情報を複製せず、必要な参照と最小限の操作情報を採用する。ハッシュ化だけで匿名化したとは扱わない。評価は§4の区分を使い、証拠不足の範囲は評価不能または再確認対象とし、法令適合は`NOT_ASSESSED`のままとする。§8.1–8.3の一次資料整理・検査提案は本番AILEXや外部AIサービスを検査した結果ではなく、新しい実装・合格実績・独立再現・認証発行を追加するものではない。

| 新規の保持シナリオ | 16/16の期待結果が一致 |
| 保存済みの署名付き入力からの再評価 | 16ケースを再評価し、ソースmanifestが一致 |
| 元の証拠評価機能の回帰テスト | 20テスト成功 |
| 元のシナリオ評価 | 23/23の期待結果が一致 |

2つのPython環境は同じシナリオを実行しており、32種類のシナリオとは数えない。新規16ケース、互換性確認の旧23ケース、VAPの既存固定53ケースを合算した適合スコアも作らない。固定版に保存されたローカルcaptureはCIの成果物とは別であり、CIの実績は上記runを参照する。本節は既存実績への文書上の参照を追加するもので、この文書更新で新たに実験や独立再現を実施したとの主張ではない。

実環境へ接続する場合は、§6に加えて、実在事業者と契約に対応する鍵・失効・信頼設定、応答を取り込む承認済み経路、リクエスト・対象・保存場所の対応、観測できない範囲を確定する。追加照会・例外承認・再確認期限・評価停止を担当する者と手順を定め、EVIDECTの評価へ変換する規則を版管理する。実験の成功は、これらの運用条件、法令適合、独立第三者認証、新たな規制義務を成立させない。

### 8.5 受信側で証拠・設定・現在時点を照合する実験

[保持証拠の受信実験](../examples/retention-evidence-intake/README.md)では、§8.4の固定版VAPアダプターを使い、元の署名付き入力から評価を再計算する。提供者が作成した判定レポートをそのまま取り込む方式ではない。仕様は独自の実験形式 `evidect-retention-intake-review/0.1` で、管理策の合否判定とは別のレビュー準備・再確認ルールを実装する。

| 別々に選択する入力 | 受信時に照合する内容 |
|---|---|
| 元のVAP入力 | 削除・保持の署名付き記録、対象、当時の評価時点 |
| 受信側の信頼設定 | 受信側が選んだ鍵・主体・役割・対象・評価時点。入力に同梱された設定への自動切替はしない |
| 証拠と設定の対応記録 | 入力と信頼設定のraw SHA-256、サービス・環境・リリース・設定・範囲・方針版・変更世代、有効期間 |
| 受信側の現在状態 | 現在として提示された設定・世代・確認時刻。対応記録の状態と別に比較する |

VAPの署名はEVIDECTの設定版や変更世代を含まないため、対応記録は受信側の判断として扱う。この記録は本実験で署名しておらず、保護・真正性・現在性は呼出し側の前提である。同じ設定へ復元しても提示された世代が異なれば再確認を要求するが、両方の状態を古いものに置き換える操作や、実環境での未観測の変更まで検出するものではない。

過去の `vap_report.as_of` と受信側の `checked_at` を区別する。保持期限や例外の終了時点をその間に越えた場合は追加確認理由を出し、過去のレポートは維持する。受信側の対応記録の失効時刻も別に照合し、保持期限と混同しない。時刻が進むことによって削除完了の申告を生成することはない。

`review_status` は `READY_FOR_SCOPED_REVIEW / REVALIDATION_REQUIRED / UNASSESSABLE` の3状態を使う。最初の状態は、提示された条件で限定的なレビューを始める準備が整ったことだけを示す。`control_status` は常に `UNASSESSABLE`、法令適合は `NOT_ASSESSED` であり、署名付き申告を§4の管理策 `PASS / FAIL` に変換する規則ではない。

実行コードは受信側に固定した22ファイルのハッシュで確認し、確認に使った同じバイトから必要なruntimeだけを一時領域へコピーして再評価する。外部checkoutの余計なモジュールや候補データを実行コードにしない。これはimportの隔離であり、OSのsandboxや実環境の安全性認証ではない。Pythonと依存パッケージ、受信側コードの管理は別の信頼前提として残る。

実行方法、入力の制限、保存した合成入力からの再評価は[実験README](../examples/retention-evidence-intake/README.md)と[入出力仕様](../examples/retention-evidence-intake/CONTRACT.md)を参照する。[保存したローカル実行結果](../examples/retention-evidence-intake/results/README.md)では4つの受信側シナリオと保存入力からの4件の再評価を確認した。本番の事業者接続・保護された信頼設定の配布・変更状態の収集・保存領域の観測は、引き続き別の接続と検証を要する。
