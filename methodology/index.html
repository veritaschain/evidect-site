TRY THE EXPERIMENTAL TOOLS

観測から報告書まで、自分の環境で試す

合成ファイルだけを使い、観測・署名・受け渡し・受取側での再検証・日本語報告書の作成を、実際のCLIで22段階にわたって確認します。正常系だけでなく、変更・鍵不足・期限切れ・改変を拒否する動作も含みます。

実験的な再現手順です。安全性の認証ではありません。

本番AILEX・AWS・顧客データには接続しません。VAP／VCPの採択済み形式や適合認証を示すものでもありません。PASSは、拒否すべき入力の拒否も含めた「テストの期待結果と一致」の意味です。管理策・法令適合はNOT_ASSESSEDのままです。

01

固定した版を確認

対象はコミットb394db7d39fbd50e54a8adae205cce594d784a32です。動き続けるmainと区別し、ソースを確認してから実行します。

02

ローカルで実行

Linux／macOS、Python 3.10以上、Node.js 22系が必要です。追加のpip／npmパッケージは不要。ソース取得にはネット接続が必要ですが、通し検証はローカルで動きます。

03

実際の結果を報告

成功・失敗・セットアップでの停止を同じ窓口で報告できます。期待値を写さず、実際に観測した結果と使用した版を記載してください。

取得と実行

自分が管理できる場所で、新しい取得先と出力先を使用してください。既存の出力先は上書きしません。以下はシェルで実行するコマンドです。このページ上でコードを実行したり、ファイルを送信したりする機能はありません。

git clone https://github.com/veritaschain/evidect-site.git evidect-reproduction
cd evidect-reproduction
git checkout --detach b394db7d39fbd50e54a8adae205cce594d784a32
git rev-parse HEAD
git status --porcelain
python3 --version
node --version
python3 -I -B tools/context-observer/walkthrough.py --output ./walkthrough-results

最後のコマンドの終了コードと、新しく作られたwalkthrough-results/summary.jsonのtest_result: PASS・22段階の結果を確認します。失敗後に古いフォルダの結果を使わず、再試行は別の新規出力先にしてください。HTMLが存在するだけでは成功ではありません。

期待する結果の読み方

正常・変更あり
ローカル検証はVALID、全体はINDETERMINATE。変更ありの記録は、正しく署名されていても再確認が必要です。
鍵・採用基準の不足、期限切れ
INDETERMINATE。必要な条件が不足しているため、比較基準として使用しません。
別の鍵・基準との不一致・改変
INVALID。確認した不一致を、合格や証拠不足に置き換えません。

外部アンカーは検証しません。署名の一致は、観測内容の真実性やサービスの安全性の証明ではありません。生成するHTML／JSON報告書は未署名で編集可能な派生物であり、原証拠や認証書ではありません。

送受信の信頼情報は同じテストプログラムが用意します。別フォルダは独立した管理者を意味しません。試験鍵と時刻は毎回変わるため、再現するのは判定・理由・終了コードであり、出力バイト列の一致ではありません。一時ファイルの通常削除は安全消去ではなく、強制終了時の残存は保証しません。

固定版の詳しい手順（GitHub） 再現結果を報告する（公開Issue）
報告は公開されます。秘密情報を添付しないでください。

秘密鍵・認証情報・顧客情報・本番ソースや設定・実運用の証拠・端末ログ一式を投稿しないでください。氏名・組織名の公開は不要です。機密性のある不具合は、公開せずsecurity@veritaschain.orgへ最小限の説明から連絡してください。

報告は内容を確認するまで自己申告として扱います。Issueの作成や同じ実装の再実行だけで、独立実装・第三者認証・法令適合の実績にはしません。このページやツールから自動で報告を送信することはありません。

01

対象・範囲を明確にする

対象、作業の目的、許可された操作、実施期間を区別します。公開情報の観測と、個別の許可を必要とする調査・作業を混同しません。

02

観測と推定を分ける

公開HTMLの製品名やバージョン表記は、観測した事実です。それだけで実稼働コードの版、修正適用の有無、脆弱性の成立や侵害を断定できません。

03

出典と確認条件を残す

参照した公式情報、確認した日時・範囲、再確認に必要な条件を所見と結び付けます。未確認事項も記載し、受け取った担当者が次の確認を判断できるようにします。

変更管理の体制と、実際の記録を照らし合わせる

継続型認証の構想では、変更の手順や責任分担に加えて、その手順が実際に機能したかを確認する設計を検討しています。対象サービス・環境・期間を定め、次の記録を結び付けます。

01

変更・検査・承認の記録

何を変更し、どの検査を行い、誰がどの版を承認したか。変更内容、検査結果、承認者、時刻を照合します。

02

本番に反映された内容

検査・承認を経た版と、実際の本番のコードや設定が対応しているか。デプロイ記録と本番環境の確認結果を照らし合わせます。

03

直接・緊急変更と再確認

通常の経路を通らない直接変更や緊急変更も対象に含め、理由、実行者、時刻、影響、事後確認を記録します。差分や記録の不足があれば、影響範囲を確認し、評価状態の見直しと再検証につなげます。

記録がそろうことと、安全な変更であることは別の確認事項です。評価では、記録の照合結果に加えて、検査の内容とその対象範囲を明示します。

記録の設計例

例：公開ページに「demo-gallery 2.3.1」と表示されていた

観測：公開HTMLに含まれた表記。
照合：デモ用アドバイザリの影響範囲。
未確認：実際のコード、個別修正、機能の有効化状況。
所見：追加確認が必要な候補。

合成データによる説明です。実在する脆弱性や調査結果ではありません。

暗号学的な記録が扱う範囲

設計上、確認を目指すこと

記録の改変の有無、記録どうしの関係、委任された範囲と操作の結び付き。VAP・OAP・DAPによる記録構成と外部アンカーの利用を検討しています。

記録だけでは保証できないこと

入力情報が真実であること、調査が網羅的であること、脆弱性の成立、侵害の有無、法的・規制上の受理。検証結果は、その前提と対象範囲に依存します。

EVIDECTの調査サービスは開発中、証跡統合は設計段階です。VAPへの適合認証や検証済みの提供サービスを表示するものではありません。
